2 Safeguards contre les fixtures en production

CODE Guard Symfony — bloquer doctrine:fixtures:load sur APP_ENV=prod ✓ ▶

Créer un subscriber sur ConsoleEvents::COMMAND qui désactive la commande avant exécution :

// src/EventSubscriber/FixtureProductionGuard.php
final class FixtureProductionGuard implements EventSubscriberInterface
{
    public function __construct(private readonly string $env) {}

    public static function getSubscribedEvents(): array
    {
        return [ConsoleEvents::COMMAND => 'onCommand'];
    }

    public function onCommand(ConsoleCommandEvent $event): void
    {
        if ($this->env !== 'prod') { return; }

        if (str_contains($event->getCommand()?->getName() ?? '', 'doctrine:fixtures')) {
            $event->disableCommand();
            $event->getOutput()->writeln(
                '<error>BLOCKED: doctrine:fixtures:load is forbidden in APP_ENV=prod.</error>'
            );
        }
    }
}

La commande est désactivée au niveau du kernel Symfony — impossible à contourner accidentellement.

CI Validation CI — TEST_DATABASE_URL ne peut pas être production ✓ ▶

Ajouter ce step avant le doctrine:schema:drop dans .github/workflows/ci.yml :

- name: Sanity check — TEST_DATABASE_URL must not be production
  run: |
    DB_URL="${{ secrets.TEST_DATABASE_URL }}"
    if echo "$DB_URL" | grep -qiE '\bprod\b|\blive\b|\bmain\b'; then
      echo "::error::TEST_DATABASE_URL contains a production keyword. Aborting."
      exit 1
    fi
    if ! echo "$DB_URL" | grep -qiE 'test|ci|staging'; then
      echo "::error::TEST_DATABASE_URL missing 'test'/'ci'/'staging'. Verify the secret."
      exit 1
    fi

Si le secret contient un mot de production ou n'a pas de mot de test, le pipeline s'arrête avant toute destruction.

DB Séparation des privilèges PostgreSQL — user applicatif sans DDL ▶

L'utilisateur app est actuellement propriétaire du schéma — il peut TRUNCATE, DROP TABLE, etc. Séparer en deux rôles :

RôleDroitsUtilisé par
app_rwSELECT, INSERT, UPDATE, DELETEApplication runtime
app_migrateDDL completMigrations uniquement

Avec app_rw, même si doctrine:fixtures:load est lancé avec ce rôle, PostgreSQL refusera le TRUNCATE.

INFRA Variable d'environnement obligatoire pour les fixtures ▶

Conditionner l'exécution à la présence d'une variable explicite ALLOW_FIXTURES_LOAD=1. Dans le guard Symfony (safeguard 1), remplacer la condition :

if ($this->env === 'prod' && !getenv('ALLOW_FIXTURES_LOAD')) {
    // commande bloquée
}

En local dev, aucun changement. En production, l'opérateur doit explicitement poser la variable dans le shell courant avant d'exécuter la commande.

3 Scénarios de suppression non autorisée

CRITIQUE DEV_AUTH_ENABLED — usurpation d'identité et suppression de decks DevAuthController.php · .env.dev:5 À corriger ▶

Quand DEV_AUTH_ENABLED=true, POST /api/dev/auth génère un JWT valide pour n'importe quel keycloakId sans authentification. La clé APP_SECRET est commitée en clair dans .env.dev.

Si activé en production ou staging : tout utilisateur peut supprimer les decks de n'importe quelle cible.

Fix : lever une exception au démarrage si DEV_AUTH_ENABLED=true et APP_ENV != dev.

#[ORM\OneToMany(targetEntity: Deck::class, mappedBy: 'user', cascade: ['remove'])]

Un $em->remove($user); $em->flush(); supprime en cascade tous ses Deck, DeckCard, et DeckUpvote. Vecteur direct : fixtures en production (cause de l'incident).

HAUTE /admin/debug-token — route supprimée AdminAuthController.php ✓ Corrigé ▶

Rend le token Keycloak brut dans une page HTML. Protégé uniquement par la vérification de session. Aucune garde contre APP_ENV=prod. XSS dans un template admin + cet endpoint = vol de token admin.

Fix : supprimer l'endpoint ou conditionner à APP_ENV=dev avec une exception au boot.

MOYENNE PATCH deckCards: [] vide silencieusement un deck entier DeckStateProcessor.php:187 À corriger ▶

mergeDeckCards() supprime toutes les cartes absentes du payload. Un PATCH {"deckCards": []} efface toutes les cartes sans validation minimum ni confirmation. Risque de perte de données sur bug client.
